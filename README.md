# AI Photo & Video Authenticity Checker

## Overview
A web application that helps users, with a focus on an accessible, senior-friendly experience, decide whether a photo or video was made by a human or generated by AI. It was built for a Software Engineering course and is organised as a **distributed system**: an interface server, one or more AI servers (workers) and a queue-based orchestrator, each running as its own Docker container.

## Features
* **Senior-friendly UI/UX:** large typography, warm high-contrast colours, clear step-by-step instructions.
* **Photo and video detection:** two custom PyTorch CNNs (`ImageCNN` for photos, `CustomCNN` for videos; video frames are sampled and their scores averaged).
* **Confidence scoring** with every prediction.
* **Safety and transparency:** mandatory disclaimers about false positives and false negatives.
* **Privacy:** no user data is stored. Uploads and results live in Redis for at most 10 minutes and are deleted as soon as they are processed.
* **Horizontally scalable:** the number of AI servers is chosen at start-up.

## Tech Stack
* **Frontend:** HTML5, CSS3 (Custom warm theme)
* **Backend:** Python, Flask, RabbitMQ (pika), Redis. ML: PyTorch, OpenCV. Deployment: Docker Compose.
* **Machine Learning:** PyTorch, Torchvision, Pillow, Scikit-learn

## Architecture

```text
Browser ─► Interface server ─► RabbitMQ queue ─► AI server(s) (workers)
               │   ▲                                   │
               ▼   └───────────── result ◄─────────────┘
              Redis (temporary files and results)
```

| Component | Folder / image | Role |
|---|---|---|
| Interface server | `interface/` | Serves the website, validates uploads, stores the file in Redis, publishes a job, returns the result. It never calls the models. |
| AI server (worker) | `ai-worker/` | Loads the photo and video models once at start-up, takes jobs from the queue, runs inference, stores the verdict. |
| Orchestrator | RabbitMQ | Central queue (`detect_jobs`) between the interface and the AI servers. |
| Temporary storage | Redis | Holds uploaded files and results with a 10-minute expiry. |

**Communication is centralised:** the interface and AI servers never talk to each other directly, only through RabbitMQ (jobs) and Redis (files and results). Jobs are acknowledged only after processing, so if a worker crashes, its job returns to the queue.

## Requirements
* **Docker Desktop** (on Windows it uses WSL 2)
* Git (to clone the repository)

## How to Run
1. Clone the repository and open a terminal in its folder:
   ```bash
   git clone <your-repo-url>
   cd <repo-folder>
   ```
2. Build and start everything, here with 3 AI servers:
   ```bash
   docker compose up --build --scale ai-worker=3
   ```
   The first build is slow because PyTorch is downloaded. RabbitMQ needs about 30 seconds to start, so wait until the workers print `Worker ready.`
3. Open the website: **http://localhost:5000**
4. Optional, RabbitMQ dashboard: **http://localhost:15672** (login `guest` / `guest`)
5. Stop everything:
   ```bash
   docker compose down
   ```

## Usage
1. Open the website and choose **Photo** or **Video**.
2. Select a single file and click the check button.
3. Wait for the analysis (videos take longer).
4. Read the classification, confidence score and disclaimer.

Limits: images up to 10 MB (JPEG, PNG, WebP), videos up to 50 MB (MP4, MOV, WebM, AVI).

## Load Test and Scaling Results
Run a load test (file, `photo` or `video`, number of requests):
```bash
python load_test.py image-2.png photo 50
python load_test.py myvideo.mp4 video 20
```
Needs `pip install requests` and a file that you supply.

## Model Details and Limitations
* The models were trained on small datasets, so real-world accuracy is limited. This is a proof of concept for the distributed pipeline, not a forensic tool.
* All servers share one queue, so a flood of videos can delay photo requests (separate queues per media type would fix this).
* The interface waits synchronously for the result (30 s for photos, 120 s for videos). A polling page would be better.
* Everything runs on one machine, so workers share its CPU. RabbitMQ and Redis are single points of failure.
* **Future work:** separate queues per media type, a polling result page, pre-trained backbones (e.g. ResNet50), deployment on separate hosts or in the cloud.
